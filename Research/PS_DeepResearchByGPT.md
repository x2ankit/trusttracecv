# Proposed CV Integrity Assurance Framework

Multi-contributor computer-vision pipelines pose unique risks: poisoned or mislabeled datasets, tampered pretrained models, and unverified inference outputs.  Prior work addresses individual facets (e.g. label cleansing, backdoor detection) but rarely offers a *unified, offline* pipeline-level solution.  We propose an end-to-end “Trustworthy CV” framework covering **Training-Data Integrity**, **Model Integrity**, **Inference Provenance**, **Distribution-Shift Detection** and **Governance**, all in a closed/offline environment.  We will integrate state-of-the-art methods and extend them for a comprehensive proof-of-concept.

## Survey of Existing Solutions

- **Training-Data Integrity:**  Tools like [Cleanlab](https://github.com/cleanlab/cleanlab) use *confident learning* to detect mislabeled samples, near-duplicates, outliers, etc.  Cleanlab automatically flags “label errors, duplicates, outliers” in image datasets using existing models.  For example, it has found thousands of label mistakes in common benchmarks.  Other approaches (e.g. *spectral signature* or *cluster analysis* on activations) can reveal poisoned samples, but Cleanlab’s general-purpose algorithms provide a strong starting point for data validation.  

- **Model Integrity (Backdoor Detection):**  A rich literature targets Trojan/backdoor detection.  **Neural Cleanse** (IEEE S&P 2019) reverse-engineers potential triggers by optimizing for minimal “mask” that causes any class to be mispredicted.  It then uses outlier analysis (e.g. median absolute deviation) on the recovered triggers to pinpoint anomalous (small) trigger patterns.  For example, the official Neural Cleanse code performs “reverse engineering” on each label and flags any trigger mask with exceptionally small norm.  **DeepInspect** (IJCAI 2019) extends this to a black-box setting: it trains a generative model to learn the distribution of possible triggers from the model’s outputs.  Both approaches aim to verify if a model has hidden behavior when a trigger is present.  

  The IARPA/NIST *TrojAI* program underscores this threat: backdoor triggers are often “rare in the normal environment” and can hide malicious behavior until activated.  TrojAI stresses that simply securing the training data or model is hard when using public datasets or pretrained models, so pipeline-level checks are needed.  The NeurIPS 2022 *Trojan Detection Challenge* confirmed that creative detectors (including trigger-search and feature-based methods) significantly outperformed naïve baselines.  We will draw on these ideas (e.g. trigger reconstruction, activation fingerprints, anomaly scoring) to assess model integrity under both white-box and black-box assumptions.  

- **Inference-Provenance (Secure Logging):**  Modern ML practices (and regulations like the EU AI Act) emphasize detailed inference logs for auditability.  An *inference log* should record for each prediction the input data (or its hash), the model version, preprocessing/configuration, and the output.  Open-source tools like **whylogs** (for data schema logging) and deployment platforms like **Seldon Core** already implement structured logging of inputs/outputs.  We will extend this by cryptographically binding each record: for example, computing a SHA-256 hash of the input image and model weights, then signing the tuple (input_hash || model_hash || output || metadata) with a private key.  This makes any post-hoc alteration or replay of the inference detectable (a mismatch in the signed record would indicate tampering).  The Practical AI Act Guide explicitly notes that an inference log allows *reconstruction* of each decision (inputs, model, output) for auditing.

- **Distribution-Shift Detection:**  Detecting covariate shift or “suspicious manipulation” of incoming data is less standardized in ML.  We will monitor statistical distances (e.g. KL-divergence, Wasserstein distance) between the current batch of inputs and a reference distribution (e.g. training data).  Methods from anomaly detection or concept-drift (e.g. monitoring average pixel or feature statistics over time) can flag sudden shifts.  For instance, an abrupt change in the distribution of feature activations can be treated as a warning sign (this is akin to out-of-distribution detection used in ML safety).  The system will score the shift and, when sufficient evidence exists, differentiate between *normal operational drift* (e.g. lighting change in camera feed) vs *potential tampering* (e.g. entirely new classes of images) based on the magnitude and pattern of the shift.

- **Audit and Governance UI:**  Every flagged issue (bad data, bad model, altered output, distribution anomaly) must be explained to a human analyst.  We will output a tamper-evident report entry for each alert, containing: a human-readable reason (e.g. “unusual cluster of image duplicates with conflicting labels”), supporting evidence (trigger visualization or statistical score), a confidence/severity metric, and a recommended action (“accept”, “review”, “quarantine”).  All alerts and logs will be stored in an immutable audit trail (e.g. append-only log or blockchain-inspired ledger) to preserve chronology.  This follows the SIH requirement that every flag include an explanation, evidence, and “tamper-evident audit trail” with declared unsupported cases.  

## Proposed Architecture and Solution

We design a **modular offline pipeline** (no cloud calls) in Python.  Key components:

- **Data Integrity Module:** Ingests the contributed dataset (COCO, YOLO, etc.) along with any available metadata (contributor, batch IDs).  It uses Cleanlab-style diagnostics to score each sample for label uncertainty and to detect duplicates or outliers.  It also runs basic data-quality checks (e.g. verify image formats, non-empty bounding boxes).  All flagged samples are aggregated per contributor: if multiple suspicious samples originate from the same source, the source gets a higher risk score (as required).  For example, if 30% of a contributor’s images are near-duplicates or have low-confidence labels, we mark that contributor’s batch as high-risk.  The module reports sample-level and source-level integrity scores.

- **Model Integrity Module:** The contributed model (ONNX, PyTorch, TorchScript) is first fingerprinted by computing a hash of its weights and architecture.  Then two analyses run in parallel:
  
  1. **Behavioral Fingerprinting:** We run a battery of *sanity checks* akin to the neural-cleanse approach.  For each output class, we optimize a minimal perturbation (trigger) to force the model to predict that class (using gradient-based search, as in Neural Cleanse).  We compute statistics (size, L1 norm) of each found trigger.  We flag the model if one trigger is an outlier – for example, a much smaller trigger achieves misclassification for one label.  We also calculate activation statistics (mean, variance) on a held-out validation set and compare to those of known-clean reference models, to catch anomalies.
  
  2. **Black-box Trigger Search:** If the model can only be queried (no internals), we apply a generative attack approach inspired by DeepInspect.  We train a lightweight generative network to produce candidate triggers that, when applied to normal images, cause the model to output a certain label.  If the generator consistently finds a pattern that induces misclassifications (beyond random chance), we mark that as evidence of a backdoor.  This step explicitly states our *access assumptions* (it only works if we can query the model’s API) and reports a confidence (how often the trigger succeeds on held-out images).
  
  In both cases, the module outputs a summary: “Model appears clean” or “Backdoor suspected in class X with trigger …” along with confidence.  All assumptions (e.g. “we treated model as black-box”) are recorded to satisfy the requirement of stating confidence and limitations.

- **Inference Log & Integrity Module:** Each time the model is run on an input image, we record a signed log entry.  Concretely, we compute SHA-256 hashes of the input image bytes and of the model’s serialized weights.  We also record any preprocessing parameters and a timestamp/sequence number.  We then concatenate `(timestamp || input_hash || model_hash || output_label || output_confidence)` and compute a digital signature (e.g. ECDSA with a project key).  The signature and all fields are stored in a local database (SQLite or JSON log).  This binding means that **any change** (to input, model, or output) would break the signature verification.  We also include a monotonic nonce to prevent replay.  In our report UI, we will display entries like:

  > **Inference #42:** Input ID 1001, Model v5b77 (hash: *abc123*), Timestamp 2026-09-30 17:25. Output: “Car” (prob 0.87). Signature OK. 
   
  This design satisfies the cryptographic linking requirement: the user can later verify that the output came from the exact input and model.  We noted (per PS) that no external APIs can be used; our solution uses only local cryptographic libraries (e.g. Python’s `cryptography` or `hashlib`).  

- **Distribution-Shift Detector:** After each batch of inferences, we update statistics on the incoming images (e.g. color histograms, texture features, activation distributions).  We compare these to reference distributions (from clean data) using statistical tests (e.g. KL divergence or maximum mean discrepancy).  If the shift exceeds a threshold (calibrated on normal drift data), we flag an “Unusual Distribution” alert.  For example, if a weather model suddenly receives night-time images instead of day-time, the detector would notice a shift and report it with a risk score.  We distinguish “normal drift” vs “suspicious” by cross-checking metadata: if contributor/source changed or if cryptographic signature logs indicate data manipulation, we bias toward “suspicious”.  In all cases, the shift detector outputs a human-readable explanation (e.g. “Brightness distribution shifted to darker images (score X)”) and a confidence in drift vs attack.

- **Analyst Report & Governance:** All findings feed into a final report schema.  For each issue (data, model, inference, or shift), we log: *Reason*, *Evidence*, *Confidence*, *Affected Asset*, *Recommendation*.  For instance, if the model integrity module finds a trigger, the log might say “Small size trigger found for class ‘Stop Sign’ (L1 norm 16.1, 3.65× MAD) – suggests planted backdoor. Confidence: 95%. Action: Review and retrain if confirmed.”  Every log entry is appended to a tamper-evident audit trail (using the same cryptographic signing mechanism), and we clearly note any **unsupported attack classes**.  For example, if we cannot access model internals, we explicitly state “Model checked with black-box method only; white-box tests N/A.”  This transparency follows the SIH requirement for a clear coverage statement.

## Implementation and Evaluation Plan

- **Data/Models:** We will use public CV datasets (e.g. COCO, CIFAR-10) and openly available models (ResNet, YOLO) as testbeds.  To simulate attacks, we will inject realistic perturbations using published benchmarks: for example, apply small image patches (backdoor triggers) to create trojaned models, or flip labels in subsets of training data.  We can leverage repositories like [BackdoorBench](https://backdoorbench.github.io) that provide a suite of attack/defense implementations, enabling reproducible evaluation.  For model integrity tests, we will also try TrojAI data or synthetic datasets with known triggers (since TrojAI specifically targets exactly this problem).  

- **Tech Stack:**  All code will be in **Python**.  We will use PyTorch (with ONNX export) and related ML libraries for loading models/datasets.  Cleanlab will be used or adapted for data checks.  For cryptography, we will use the `cryptography` package (ECDSA or similar) and `hashlib` for hashing.  The database can be SQLite or JSON files (no external dependencies) to store logs and results.  The interface can be a simple Jupyter-based dashboard or CLI that displays alerts in table form.  Our architecture (modules and data flow) will be documented, as required.

- **Offline Operation:** All components will work without internet.  We will bundle needed frameworks (e.g. via pip/conda).  No calls to cloud or external APIs will be made.  Any “reference model” needed for tests (e.g. a clean ResNet) will be pre-downloaded or built and cached.  This respects the PS constraint of an air-gapped workflow.

- **Testing:**  We will create test cases covering each PS requirement:
  - **Data Integrity:** Datasets with some mislabeled or duplicate images, and verify Cleanlab flags them.  
  - **Model Integrity:** Known backdoored models (e.g. hidden trigger in ResNet) should be detected by our NeuralCleanse/DeepInspect modules.  
  - **Inference Logs:** We’ll simulate replay/tamper by altering log entries and show the signature fails verification.  
  - **Distribution Shift:** We will feed the system data from a shifted distribution (e.g. new scene types) and check that it reports a shift score.  
  - **End-to-End:** Finally, a fully poisoned dataset + model scenario should trigger alerts in all relevant modules, culminating in a consolidated report.

Each test will produce an “assurance report” (JSON or HTML) with findings.  We will also record execution logs to prove reproducibility (e.g. fixed random seeds, dockerfile).  The SIH expects source code and a “reproducible audit log” – our signed inference records and modular code will satisfy this.  The final submission will include a clear statement of what attacks we covered (e.g. image patch backdoor, label flips, replay attacks) and what we assume (e.g. generator trigger only if black-box, white-box only if weights available).

## Novel Contributions

Our solution goes beyond existing tools by **integrating** them into one coherent workflow.  Instead of separate detectors for data vs model vs inference, we provide end-to-end traceability.  For instance, if the data module flags contributor A for suspicious labels, and the model module then identifies a backdoor related to a class predominant in A’s data, the system can correlate those findings.  We will also innovate in the tamper-detection domain: while prior work suggests logging, we will implement a *cryptographically verifiable* inference ledger, which (to our knowledge) is not standard in academic toolkits.  Finally, we must balance “low submissions” vs robustness: we aim for technical depth (rigorous anomaly detection, security logging) rather than a superficial solution.
